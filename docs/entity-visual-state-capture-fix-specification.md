# Entity visual state capture and identity rewrite specification

## Status

Implemented on `codex/fix-entity-visual-state-capture`. Both adapter production
source sets compile against their version-specific mapped server artifacts. The
complete Paper 26.2 adapter suite passes 43 tests and the complete Paper 26.3
adapter suite passes 44 tests in direct JUnit execution.

## Objective

Correct three playback defects on Paper 26.2 and Paper 26.3 without weakening
the neutral-observer boundary:

1. a recorded player's held items and armor did not follow later changes;
2. a recorded player's arm-swing animation could be absent; and
3. a firework rocket used for Elytra boosting could attach to the live observer,
   causing its client-side particles to follow the observer instead of the
   isolated replay entity.

The implementation must retain version-specific native packet handling,
recording-scope coordinates, capture ordering, checkpoint reconstruction, and
compatibility with existing replay artifacts. Capture-source selection follows
the project-wide [capture source policy](capture-source-policy.md).

## Findings

### Player state is not represented by a reliable self-bound clientbound stream

Paper normally broadcasts movement, equipment, and swing presentation to
tracking players. A client already knows about its own accepted input, so the
server does not need to send every presentation packet back to that player. If
no other player tracks the actor, an outbound-only global capture can therefore
miss state required by replay.

The previous movement fallback used `PlayerMoveEvent`. Extending that design to
equipment and swings would make player replay state increasingly dependent on
gameplay events even though the client protocol already exposes the accepted
player input. The implemented design instead treats accepted PLAY serverbound
packets as the player-state trigger.

PacketEvents receive callbacks may run on a Netty event loop. The callback reads
only PacketEvents-owned immutable semantics: user UUID, protocol entity ID,
packet type, animation hand, and capture tick. It never reads a Bukkit location,
inventory, CraftBukkit handle, or mutable world object. One coalesced scheduler
task per pending player performs authoritative state sampling on the server
thread.

### Equipment needs state comparison rather than inventory-event inference

The server-thread sample reads every native equipment slot. It compares the
current copied `ItemStack` values with the previous sample and emits one
`set_equipment` packet containing only changed slots. The first sample contains
all slots, and an empty item is retained when a slot was cleared. This covers
held items, armor, durability/components, and server-side changes visible at the
next accepted packet without combining multiple inventory event families.

Paper can represent an exact main-hand/off-hand exchange as the `SWAP_HANDS`
entity event. Once the adapter owns equipment for an entity, this recipient copy
and recipient-derived `set_equipment` packets are suppressed so a client cannot
apply the same swap twice.

### Swings are ephemeral and version-specific

The accepted serverbound animation packet contains the selected hand. The hand
is queued with the coalesced state sample and converted into the adapter-native
clientbound representation:

- Paper 26.2 emits `ClientboundAnimatePacket` with `SWING_MAIN_HAND` or
  `SWING_OFF_HAND`.
- Paper 26.3 emits `ClientboundSwingAnimationPacket` with the selected NMS hand
  and the current item's swing-animation component.

A recipient-derived swing for the same entity is suppressed only during the
accepted packet's server tick. Critical-hit and other animation actions remain
capturable on 26.2, and later plugin-originated swings remain capturable on both
versions. Swings stay transient and are not applied during seek reconstruction.

### Firework attachment is a synchronized entity reference

The Elytra firework effect is generated by the client from the spawned rocket.
The rocket's synchronized data contains `DATA_ATTACHED_TO_TARGET`, serialized as
an `OptionalInt` by `EntityDataSerializers.OPTIONAL_UNSIGNED_INT`. Its value is
the boosted entity's protocol ID.

The playback rewriters already remapped the outer `set_entity_data` packet ID,
UUIDs, `Optional` values, and lists, but did not remap `OptionalInt`. The rocket
could consequently retain a recorded entity ID that belongs to the live
observer in the playback connection.

Mapped Paper 26.2 and Paper 26.3 sources show that
`OPTIONAL_UNSIGNED_INT` is used for verified entity references in these
versions: firework attachment targets, frog tongue targets, and player
shoulder-parrot references. The rewriter now maps a present `OptionalInt` only
when that serializer is present. An empty value remains empty, while normal
integer metadata is left unchanged.

## Implemented design

### Capture bridge

`Paper26CaptureBridge` and `Paper26_3CaptureBridge` use one PacketEvents listener
for both directions. Existing clientbound packets continue through registry
classification and capture-context resolution. Accepted PLAY serverbound
packets are delegated to the version-specific entity-state coordinator; their
raw serverbound payloads are not stored in the replay artifact.

Synthetic state uses the same capture-order allocator and packet sink as normal
clientbound capture. The emitted context contains the actor's world and block
position, so a bounded recording is evaluated against the scene entity rather
than an arbitrary recipient.

### Player-state sampler

`Paper26PlayerStateCapture` and `Paper26_3PlayerStateCapture` own:

- thread-safe coalescing by PacketEvents user UUID;
- queued main/off-hand animation requests;
- server-thread Bukkit/NMS lookup;
- movement and equipment snapshots; and
- emission of version-specific changed state.

Only a UUID and packet-owned semantics cross the Netty-to-server-thread
boundary. Pending state is discarded when capture closes or the player is no
longer online.

### Entity-state coordinator and fallbacks

`Paper26EntityStateCapture` and `Paper26_3EntityStateCapture` coordinate the
player sampler, duplicate index, and lifecycle cleanup. They retain Paper events
only for non-player entities:

- `EntityMoveEvent` supplies movement for an entity without an owner connection;
- `EntityEquipmentChangedEvent` supplies changed equipment for a non-player
  living entity; and
- entity removal clears retained protocol IDs and player snapshots.

Player movement, player equipment, and player arm swings do not use Paper or
Bukkit gameplay events.

### Native packet factory

Packet construction is isolated in `Paper26EntityPacketFactory` and
`Paper26_3EntityPacketFactory`. This keeps protocol differences out of the
coordinator and sampler. In particular, 26.2 uses `PositionMoveRotation` and the
legacy animate action, whereas 26.3 uses `PositionPath` and the dedicated swing
packet.

### Authoritative-state index

`Paper26AuthoritativeStateIndex` and
`Paper26_3AuthoritativeStateIndex` parse only verified packet shapes. They track
movement and equipment authority for an entity lifetime and swing authority for
one server tick. The capture bridge asks the index before publishing a normal
clientbound frame, preventing recipient count from duplicating recorded state.

### Playback identity rewrite

Both replay packet rewriters pass the metadata serializer into value rewriting.
The rule is:

```text
serializer == OPTIONAL_UNSIGNED_INT and value is present
    -> OptionalInt.of(mapEntityId(recordedId))
serializer == OPTIONAL_UNSIGNED_INT and value is empty
    -> OptionalInt.empty()
all other values
    -> existing recursive metadata rewrite
```

The rule is serializer-qualified and does not reinterpret arbitrary integer
metadata as an identity.

## Checkpoint and artifact compatibility

No public API, configuration, database schema, replay artifact schema, packet
registry fingerprint, or adapter format revision changes.

- Snapshots already contain current equipment and entity metadata.
- Live equipment deltas remain checkpoint-relevant.
- Entity metadata remains checkpoint-relevant, including firework attachment.
- Swing animations remain non-checkpoint transient frames.
- Existing artifacts remain readable and benefit from the corrected metadata
  identity rewrite.

Equipment or swing frames that were absent from an older recording cannot be
reconstructed retroactively.

## Validation

Adapter tests cover:

- movement and equipment duplicate suppression;
- hand-swap suppression;
- same-tick swing suppression and later-tick preservation;
- non-swing 26.2 animation preservation;
- initial, unchanged, changed, and cleared equipment slots;
- 26.2 main/off-hand animate encoding;
- the 26.3 dedicated swing rewrite; and
- present and empty `OPTIONAL_UNSIGNED_INT` values while preserving an ordinary
  integer metadata value.

The two adapter production source sets and all adapter tests are compiled
against their respective mapped Paper server and API artifacts. Direct JUnit
execution completed with 43/43 Paper 26.2 tests and 44/44 Paper 26.3 tests.
Full Gradle execution remains the preferred regression command:

```text
./gradlew :replay-adapter:paper-26_2:test
./gradlew :replay-adapter:paper-26_3:test
./gradlew :replay-core:test
./gradlew test
```

Manual verification should record a single player with no other tracking player
online, change and clear held/armor slots, swap hands, use both swing hands, and
boost an Elytra flight with a firework. Playback as the same account must show
the changes on the isolated replay entity, keep the rocket and particles on that
entity, and leave the neutral observer unchanged. Seeking across an equipment
change must reconstruct equipment without replaying historical swings.
